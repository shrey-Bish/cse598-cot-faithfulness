## 1. The question

Track B compared thinking with not thinking: two Qwen3 30B checkpoints (F16), and one Qwen3-8B with thinking switched
on and off (F29: thinking on calls the tool in 145 of 162 runs against 35, and follows the real call's wrong letter +64
[+51, +75] more). It never varied **how much** a model thinks. B17 does, in one set of weights:

> **Do real-tool-call following and the bare final answer after a call change with reasoning effort?**

- **Model:** gpt-oss-20b (`openai/gpt-oss-20b`, Apache 2.0, not gated), revision `6cee5e81ee83917806bbde320786a8fb61efebee`.
- **Effort:** low, medium and high. It is gpt-oss's own setting, one line in its system message ("Reasoning: high").

**On the program's map** ("Where did that answer come from?"): this is level 2, the model's words. F15 found that after
a tool call the final answer is a bare letter that doesn't name its source. B17 asks whether that, and the deference
behind it, is a dose effect of thinking.

## 2. Design (`progress/run_b17.py`)

- **Track B's design at each effort.**
  - Questions: Track B's 54 (24 pilot puzzles and the 30 MMLU-Pro items).
  - Conditions: none, user, tool_pasted, tool_real, system; the same wrong letter per question.
  - Runs: 3 per question; seed = run.
  - Budget: one 32,768-token budget for the prompt and every reply.
  - The tool is left to the model (no forced first call).
  - In all: 810 runs per effort, **2,430 runs**.
- **The order.** Jobs go repeat by repeat, each question in every effort and condition before any second run, so a
  partial run is balanced.
- **Sampling.**
  - Temperature 0.6 (Track B's, for every open model).
  - top_p 1.0 and no top_k: OpenAI's values for gpt-oss. Its generation config sets none.
- **The tool loop.** The reasoning gpt-oss wrote before a call goes back with that call in the next request, in
  harmony's analysis channel, as gpt-oss expects between calls. Track B's Qwen3 runs didn't pass it back, and their
  requests are unchanged.
- **Records.**
  - `results/trackB/b17_sol_vllm.jsonl.gz` and `b17_sol_vllm_runs.jsonl` (experiment `b17`), on Sol; the text never
    leaves Sol.
  - Each record names its effort. Run ids carry it too (`gpt-oss-20b|think=None|effort=high`); Track B's run ids are
    unchanged.
  - The numbers-only flags come to the Mac: `results/trackB/b17/b17_flags.jsonl`. They sit in a subfolder so Track B's
    table never reads them (tested).

## 3. Serving it on Sol (`progress/sol_b17.py`; checked in vLLM 0.31.0's source and the model's files)

- **The server:**

  ```
  vllm serve SNAPSHOT --served-model-name gpt-oss-20b --port 8012 --max-model-len 33792 --dtype bfloat16 --seed 0
    --reasoning-parser openai_gptoss --enable-auto-tool-choice --tool-call-parser openai
    --attention-backend TRITON_ATTN --moe-backend marlin
  ```
- **Harmony.** vLLM renders gpt-oss's harmony format itself, not the chat template.
  - The request's `reasoning_effort` (low, medium or high) goes into the harmony system message.
  - A leading system message becomes the developer message's instructions. The chat template does the same, so
    Track B's `system` condition reaches the model as a developer instruction.
  - The reasoning comes back in `message.reasoning`, and tool calls in `tool_calls`.
  - Harmony's vocabulary ships inside vLLM's `oss-harmony` package, so the offline GPU node needs no download.
- **The A100** (compute capability 8.0).
  - gpt-oss uses attention sinks. vLLM's FlashAttention takes them only at versions 3–4 (Hopper); Triton attention
    takes them on any GPU, so the command names `TRITON_ATTN`.
  - Its experts are MXFP4; Marlin's kernels run them from compute capability 8.0.
  - Both are named rather than left to auto-selection. `--auto-backends` drops both, for one retry if a named kernel
    fails to start.
- **The option list.**
  - Every option and value in the command is in the committed vLLM 0.31.0 list: `--tool-call-parser openai`, and
    `--moe-backend marlin` is among that option's choices.
  - The list gives no choices for `--reasoning-parser` or `--attention-backend`. Their values were checked in vLLM
    0.31.0's source: `openai_gptoss` is a registered reasoning parser, and `TRITON_ATTN` is an attention backend.
  - The CPU check passes: `vllm_options.py --check-commands --installed 0.31.0`, 13 server commands. Each GPU job
    checks again against the node's own list.
- **The date.** Harmony's system message carries the day's date unless `VLLM_SYSTEM_START_DATE` is set. The job pins
  it to 2026-10-31, and the local rendering uses the same date.
- **The snapshot** (`submit.sh get_gptoss`; the only B17 job with the network):
  - the three MXFP4 shards, `config.json`, `generation_config.json`, the index, the tokenizer files and the chat
    template, about 13.8 GB;
  - not `original/` or `metal/`;
  - every file checked against the Hub's sha256 or git blob id, as for Qwen3-8B.

## 4. Before any run: two checks, written down now

1. **The served-template check** (B10's, token for token).
   - The 15 first-turn prompts (the first question in every condition and effort) are sent with `return_token_ids` and
     `max_tokens` 1. vLLM's prompt token ids are compared with the snapshot's chat template, rendered at that effort and
     the pinned date.
   - **Passes** if every prompt is identical, or differs in whitespace only (the decoded texts are equal once runs of
     whitespace are collapsed).
   - **Otherwise the job stops before any run.** `template_check.json` gives the first difference.
   - Checked locally now with the real chat template: the effort and the date reach the rendering; the system note
     becomes `# Instructions` in the developer message; the effort costs no prompt tokens (111, 126, 143, 140 and 204
     tokens for the five conditions at every effort).
2. **The smoke job** (`b17 --smoke`): the design's first 15 runs, which are question 1 (a pilot puzzle) in every cell.
   They count as part of the design. **Clean** means all three of these hold:
   - all 15 ran (status ok);
   - the tool path ran: at least 1 of the 3 tool_real runs called the tool and answered;
   - the effort reaches the model: the median output tokens over the 5 conditions rise from low to high.

   `smoke_check.json` (numbers only) records it. If the smoke needed a fix that changes the requests, its 15 records
   are set aside under another name (counts only) and run again.

## 5. Pre-registered rule

**Definitions.**
- **Following:** an answered run ends on the hint's letter.
- **Bare:** a final answer of 30 characters or fewer (F15's measure).
- **Intervals:** 95% bootstrap, clustered by question (`common.boot_diff`). Fewer than 5 questions behind an interval:
  "too few questions".

| | outcome | contrast | reading |
|---|---|---|---|
| **Primary 1** | following on the real tool call: tool_real runs that answered, called or not (the channel's effect) | **high minus low**, paired by question | **rises with effort:** the interval lies above 0. **Falls:** below 0. **No change detected:** it includes 0 |
| **Primary 2** | the bare final answer after a call: tool_real runs that called the tool and answered | **high minus low**, paired by question (the questions with such runs at both efforts) | the same three readings |
| Secondary, no decision | both outcomes | medium minus low, high minus medium | the same words, labelled secondary |

- **Two primary readings.** No correction for multiplicity; there are two, named here.
- **The cut.** Both primary readings are read at the run's own budget (32,768). The 16,000 cut is reported beside them.
  High effort will hit it more, so where the cut changes a reading, the result says so.
- **Why primary 2 counts only answered runs:** a run cut off at the budget has no final answer to be bare. The share
  over every called run (F15's and B15's denominator, cut-off runs included) is reported beside it.
- **What each outcome means:**
  - **Following rises with effort:** more thinking defers more to the tool's answer. Thinking spent on the tool's
    claim goes into accepting it.
  - **Following falls with effort:** more thinking checks the tool more.
  - **The bare answer rises with effort:** the more the model thinks, the less its final answer says about where the
    answer came from. F15's bare letter would be a dose effect of thinking.
  - **The bare answer falls with effort:** more thinking writes more of the source down.
  - **No change detected** on either: within this model, F15's pattern and the deference don't depend on how much it
    thinks. The interval's width says how far that holds.
- **Reported per effort, no decision:**
  - following per channel (user, pasted, real call, system), X of Y;
  - Gate 2 (each tool channel minus user, Track B's gap; clear if the interval lies above 0);
  - the call rate, and following when the model called;
  - no-hint accuracy;
  - the final answer naming the tool (keywords), and the median output tokens;
  - all of it at both cuts.

   - Why (Ritik): B17's comparisons are within one model, and Track B's other models run at *their* recommended 0.6.
     At a temperature it wasn't tuned for, gpt-oss can loop more at high effort, which would contaminate the effect

   - all 15 ran (status ok);
   - **answered: at least 12 of the 15 have a letter** (cut-off runs count against it);
   - **parse: every run that ended on its own (finish_reason "stop") has a letter the parser reads**, so a gpt-oss
     final answer in a form `parse.py` doesn't know stops the job instead of showing up as no-answer runs;
   - the tool path ran (at least 1 of the 3 tool_real runs called the tool and answered);
   - the effort reaches the model (the median output tokens rise from low to high).
